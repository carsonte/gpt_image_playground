# 上游同步与服务器更新流程

## 核心规则

服务器只部署我们自己仓库的 `stable` 分支，不直接拉取原作者仓库。无论变更来自原作者还是我们自己，都必须先在本地完成检查和验收。

```text
原作者 upstream/main ─┐
                     ├─> 本地集成与排查 ─> origin/stable ─> 服务器一键更新
我们的本地改动 ───────┘
```

这样可以同时保留原作者后续优化和我们的后台、公告、统计、日志、服务端代理等定制功能。

## Git 远程仓库规划

正式部署前使用两个远程仓库：

- `upstream`：原作者仓库 `https://github.com/carsonte/gpt_image_playground.git`，只用于获取作者更新。
- `origin`：我们自己的私有仓库或专用部署仓库，用于保存定制版本和发布 `stable`。

当前本地的 `origin` 仍然指向原作者仓库。创建好自己的仓库后再执行远程地址调整，避免误推送到原作者仓库。

## 原作者发布新版本时

1. 获取 `upstream/main` 的新提交，但不直接更新服务器。
2. 创建独立集成分支，例如 `integration/upstream-20260821`。
3. 检查上游差异，重点关注：
   - `src/store.ts` 的持久化与数据迁移。
   - API Profile、代理请求和生图响应格式。
   - Vite 构建环境变量与 Docker 配置。
   - 我们新增的 `/admin`、公告、统计、日志和服务器 API。
   - SQLite schema 是否需要向前兼容迁移。
4. 合并上游并逐项解决冲突，不以简单覆盖我们的定制代码作为解决方案。
5. 执行发布验证：

   ```bash
   npm run verify:release
   ```

6. 在本地浏览器验收前台生图、公告、后台登录、数据看板和日志。
7. 验收通过后才将该版本合入并推送到我们自己的 `stable` 分支。
8. 在服务器运行 `bash deploy/update-server.sh`。

如果上游更新暂时不兼容，就保留当前 `stable` 线上版本，在集成分支继续修复；服务器不受影响。

## 我们自己发布新功能时

流程相同：本地开发完成后先执行 `npm run verify:release`，再做浏览器验收。只有确认通过的提交才进入 `stable`，随后运行服务器一键更新脚本。

## 更新失败处理

- 构建失败：旧容器继续运行，不切换版本。
- 新版本健康检查失败：自动恢复旧镜像和更新前数据库。
- Git 分支存在分叉或服务器有代码修改：停止更新，等待人工排查。
- 上游发生较大架构变化：继续使用当前 `stable`，不要强行上线。

API Key、后台密码和随机密钥保存在服务器的 `deploy/.env.server`，不进入 Git，也不会被代码更新覆盖。SQLite 数据保存在 `deploy/data/`，每次更新前自动备份。
