# 4K 图片编辑超时排查与后续计划

更新时间：2026-08-29

## 当前结论

- 故障发生在上传图片后的编辑接口 `/images/edits`，不是普通文字生图。
- 两次失败请求均为 4K 竖图 `2304x3456`，线路都是 `Sixoner → BlackEngine`。
- Sixoner 均先返回 HTTP `524`，表示其网关等待上游生成超时。
- 自动切换到 BlackEngine 后，响应传输阶段均出现 `Premature close`，即上游在完整响应传完之前关闭了连接。
- 两次请求最终均失败，耗时分别约 185 秒和 181 秒，没有输出图片。
- 同参数的合成图片直连复测中，Sixoner 和 BlackEngine 都能成功，因此当前证据更符合上游瞬时拥堵、真实输入复杂度或大图/遮罩处理耗时触发超时，而不是固定的请求字段错误。

## 2026-08-29 本次实现

- `application/json` 图片响应默认先在服务端完整缓冲，单响应上限为 32 MiB；确认 JSON 完整后才向浏览器发送。
- 响应头、响应体、浏览器返回分别记录阶段耗时；响应体中途关闭或 JSON 不完整且尚未发送响应头时，会按原回退链尝试下一条线路。
- 每次尝试记录线路、模型、HTTP 状态、请求 ID、输入图片数量与字节数、遮罩存在性、响应字节数、阶段和回退次数；日志只保存元数据与脱敏错误摘要。
- SSE 等非 JSON 响应继续使用流式转发，不做整响应缓冲。
- `scripts/server-smoke.mjs` 新增响应体中途断开场景，验证 CatAPI → Sixoner 回退、阶段日志和最终成功记录。
- 浏览器错误详情会显示代理返回的 `X-Request-Id`，便于与后台日志和生成记录关联。

## 后续评估

### 已完成：补齐每次线路尝试的诊断数据

`image.proxy_fallback` 和最终日志现在包含以下字段：

- 每次线路尝试的开始时间、响应头耗时和响应体传输耗时。
- 输入图片数量、输入文件总字节数、是否包含遮罩；不保存图片内容。
- 当前线路、模型、HTTP 状态、失败阶段（连接、等待响应头、读取响应体、返回浏览器）。
- 对 `524`、`Premature close`、本地超时和用户主动取消使用不同的中文错误说明。

### 已完成：避免只显示“请求中断”

- 前台在全部线路失败时展示最后错误阶段和请求 ID。
- 后台报错记录将同一请求的每次回退日志和最终错误串联展示，可看到“Sixoner → BlackEngine”等线路过程。
- 逐步回退提示仍需前端实时事件通道，暂不在本次范围内。

### 已完成：优化成功响应的转发方式

JSON 成功响应现在会先完整读取；如果上游在响应体中途关闭连接，会在发送浏览器响应头前触发回退。

下次评估：

- 默认缓冲上限固定为 32 MiB；超过上限会记录 `response_body` 阶段错误并按回退规则处理。
- SSE 等非 JSON 响应仍保持流式转发；浏览器已经收到响应头后不再尝试重复发送回退结果。

### P1：设计图片编辑的降级策略

- 4K 编辑全部失败时，可提示用户选择“降为 2K 重试”。
- 是否自动降级必须做成后台开关；默认建议询问用户，避免重复计费和输出规格变化。
- 不建议对未知状态的请求盲目自动重试，以免上游实际已经生成并重复计费。
- 可评估为图片编辑单独配置线路顺序，与普通文生图分开。

### P1：检查基础设施超时

- 核对宝塔 OpenResty 的 `proxy_connect_timeout`、`proxy_send_timeout` 和 `proxy_read_timeout`。
- 当前 Sixoner 的 524 是其上游网关返回，不能只靠调整本站 OpenResty 解决。
- 检查 BlackEngine 是否对大响应、Base64 或长时间图片编辑存在连接时长限制。

## 验收标准

- 任意失败都能看出具体线路、模型、失败阶段、耗时和请求 ID。
- 同一请求的所有回退记录可以在后台串联查看。
- 上游响应中断时不再只显示无法解释的“请求中断”。
- 4K 图片编辑失败时有明确阶段、线路和请求 ID；是否提供 2K 重试仍作为后续产品策略评估。
- 不记录或保存用户上传图片；日志只保存必要的尺寸、字节数和错误摘要。
